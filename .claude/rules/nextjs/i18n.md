# Internationalisation (next-intl)

- Aucun texte d'interface en dur, y compris `aria-label`, `alt`, `title`, `placeholder`
- Locale toujours dans l'URL (`/[locale]/…`) ; configuration unique dans `shared/i18n/routing.ts`
- Navigation via `shared/i18n/navigation` (`Link`, `redirect`, `useRouter`, `usePathname`), jamais `next/link` ni ces helpers de `next/navigation`
- Messages typés ; ICU pour pluriels et variables ; jamais de concaténation de chaînes traduites
- Toutes les locales ont exactement les mêmes clés
- Messages d'une feature dans `features/X/messages/<locale>.json`, exposés par un chargeur (`loadXMessages(locale)`) dans son `index.ts` ; assemblés dans `app/_i18n/request.ts` (point d'entrée de next-intl) par la fabrique générique `createRequestConfig` de `shared/i18n`, qui n'importe aucune feature
- Erreurs : `t('errors.<code>')` avec repli générique ; le `message` backend n'est jamais affiché
- Dates : `useFormatter` / `getFormatter` avec fuseau explicite ; jamais `toLocaleString()` ni `format()` de `date-fns` pour afficher
- `date-fns` réservé aux calculs d'interface (plages, bornes) ; calculs métier au backend
- `<html lang>` suit la locale ; la locale est transmise au backend (`Accept-Language`)
